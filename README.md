# Dating Joyce — Engine Extract

Selected systems code from **Dating Joyce**, a deckbuilding dating sim I designed, built and
released commercially as a solo developer.

Built in [Ren'Py](https://www.renpy.org/) (Python). Released on Steam, itch.io and DLsite,
**2,000+ copies sold**, localized into 4 languages, shipping to Windows, macOS, Linux, Android
and web from a single codebase.

> **Note on content.** Dating Joyce is an adult visual novel, and its
> [Steam page](https://store.steampowered.com/app/2832580/) is age-gated. **This repository
> contains no art, audio, or narrative script** — only the engine and interface code, published
> as a portfolio extract. Everything below is safe to read at work.

## What's in here

| File | What it demonstrates |
|---|---|
| [`src/cards/2__Card_&_Deck.rpy`](src/cards/2__Card_&_Deck.rpy) | The `Card` and `Deck` classes — runtime effect evaluation, draw/discard/shuffle piles, procedural card art composition |
| [`src/cards/3__Cards.rpy`](src/cards/3__Cards.rpy) | All 59 card definitions as data: effects, conditions, costs, rarity and act-gating in one declarative table |
| [`src/ui/2__Languages.rpy`](src/ui/2__Languages.rpy) | Per-language font stacks with CJK fallback chains |
| [`src/ui/2__Screens.rpy`](src/ui/2__Screens.rpy) | Custom UI — paginated deck viewer, card hover/zoom, hand management |
| [`src/ui/2__Styles.rpy`](src/ui/2__Styles.rpy) | Custom render layers and transition handling |

The `1__` / `2__` / `3__` filename prefixes are load-order control: Ren'Py parses files
alphabetically, so the numbering enforces dependency order between definition passes.

## Design notes

**Cards are data, not code.** Every card is a dict entry in `cardList` with an optional `cond`
(when it can be played) and `eff` (what it does), both evaluated at runtime. A card with no `eff`
falls back to calling a label named after it by convention, so simple cards need zero
boilerplate and complex ones drop into full script. Adding a card is one table entry.

**The main menu is a hand of cards.** 12 of the 59 definitions aren't gameplay cards at all —
"Start a New Game", "Change Language" and the rest are entries in the same `cardList`, drawn and
laid out by the same code. Reusing the card renderer for the menu meant the title screen came
almost free, and the menu inherited hover states, translation-aware text scaling and layout
for nothing.

**Card art is composited, not drawn.** `Card.updateArt()` builds each card from a tinted
background, an illustration and a text box, with the frame colour derived from the card's stat
category. Hover states are generated by matrix-colorizing the composite, so no card needs a
second hand-drawn asset.

**Translated text has to fit art it was never designed for.** Card frames are fixed-size, but
a 12-character English effect can become a 30-character French one. `updateArt()` measures the
*translated* string — stripping variable interpolations and style tags first — and scales the
font down on a curve, with a separate curve for Chinese and Japanese, where glyphs are denser
and the same character count needs much more room.

**CJK support is a font-fallback problem.** Latin display faces have no CJK coverage, so
`2__Languages.rpy` builds per-language `FontGroup` chains that map Unicode ranges to different
files — keeping the game's display font for Latin glyphs while falling through to Noto/GenJyuu
for CJK — and adjusts line spacing per script.

## Systems not included in this extract

These are part of the shipped game but live in files interleaved with narrative content:

- **Steamworks achievements** with notification and sync
- **Roguelike mode** — a separate run-based mode with its own card shop and coin economy
- **Build packaging** — one tree producing demo, censored and full SKUs via build classifiers,
  plus Android and web builds with progressive asset download rules
